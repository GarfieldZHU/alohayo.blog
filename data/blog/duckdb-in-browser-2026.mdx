## Why IndexedDB lost (and it's not IndexedDB's fault)

Let me be honest: IndexedDB is not a bad database. It's a great **transactional key-value store**. It's *not* an analytics engine — and nobody ever claimed it was. The problem is that if you want to aggregate a dataset in the browser, you have to:

1. `getAll()` every single record out of IndexedDB into memory
2. Write a JavaScript `Map`/`reduce` loop to group and sum
3. Sort the results yourself

That's a full scan + manual aggregation in a single-threaded JS context, row by row. On 50K rows it takes 2.8 seconds. On 1M rows it would take a minute. No `WHERE` pushdown, no columnar layout, no vectorization — just you and your `for` loop.

SQLite-Wasm did better (~80ms) because it has a real SQL engine — but it's still **row-oriented**, which means `SUM(amount)` still touches every row's full record, not just the `amount` column.

DuckDB is **columnar**. `SUM(amount) GROUP BY region, product` only reads the three columns it needs, in vectorized batches, with predicate pushdown. That's why it finishes before the other two have even loaded.

## What it took to make this work (the traps)

Getting DuckDB-Wasm into a Next.js blog was *not* "npm install and done". Three real walls I hit:

### 1. CSP hates CDN workers

My blog has a strict Content Security Policy in `next.config.js`. The first version loaded DuckDB's worker from `cdn.jsdelivr.net`:

```
worker-src 'self' blob:
```

Chrome immediately blocked it:

> Creating a worker from 'https://cdn.jsdelivr.net/...' violates the following Content Security Policy directive: "worker-src 'self' blob:"

**Fix:** self-host the wasm binaries and worker scripts under `public/vendor/`. Now everything loads from the same origin, CSP stays strict, and there's no runtime dependency on a CDN. Win-win-win.

### 2. Import the right bundle

`import * as duckdb from '@duckdb/duckdb-wasm'` made Next.js/webpack pull in the **Node** build (`duckdb-node.cjs`) during SSR, with a scary `Critical dependency` warning. The package has a `browser` export condition, but webpack didn't honor it the way I expected.

**Fix:** import the browser bundle directly:

```ts
import * as duckdb from '@duckdb/duckdb-wasm/dist/duckdb-browser.mjs'
```

### 3. SQLite-Wasm's API is NOT sqlite3's C API

I wrote `stmt.free()` because that's what sqlite3 C API has. At runtime:

> TypeError: stmt.free is not a function

The `@sqlite.org/sqlite-wasm` ESM wrapper's prepared statements use **`finalize()`**, not `free()`. One word, one wasted debug session.

## When is this actually the right architecture?

The pattern — **ship the query engine with the app, keep the data local** — is not a gimmick. It's the architecture behind real tools:

- **Observable / Evidence / Rill** — BI tools built on DuckDB-Wasm as their embedded engine
- **GeoLibre** — a whole GIS stack running in the browser with DuckDB-Wasm Spatial
- Server costs go to ~zero: the user's machine does the compute, your CDN only serves a few MB of wasm + Parquet

It wins when your data is **modest-sized (≤ ~2GB), read-mostly, and privacy-sensitive**. It's wrong when you need concurrent writers, petabyte scale, or centralized governance — then keep your warehouse.

My mental model, from the earlier DuckDB/Postgres/SQLite comparison:

| Tool | What it is |
|---|---|
| Local files | just data |
| SQLite | database for your app |
| **DuckDB** | **SQL analytics over local data** |
| PostgreSQL | shared DB server for many users |
