# WebGPU + WASM MDX runner

This repository now has a small, client-only playground for the draft WebGPU article at `data/blog/webgpu.mdx`.

## What it demonstrates

The playground has three separate boundaries:

```text
MDX article
    |
    v
WebGpuWasmPlayground (client React component)
    |                         |
    v                         v
editable WAT -> .wasm    WebGPU canvas + WGSL
    |
    v
export shade(i32) -> i32
```

The editable source is compiled into a real WebAssembly binary in the browser. The exported `shade` function receives the slider value. Its result becomes a color in a WebGPU uniform buffer, and a WGSL triangle renders that color.

The component is mapped from `components/MDXComponents.tsx`, so an MDX post only needs:

```mdx
<WebGpuWasmPlayground />
```

## Why the editor is WAT, not arbitrary Rust

`rustc` and the Rust standard library are not small browser dependencies. A full Rust-in-the-browser editor would need one of the following:

- ship a large Rust toolchain and compile locally;
- call a remote build service, which introduces latency, credentials, and code-handling concerns; or
- use a hosted IDE/editor and embed it.

The article instead uses a deliberately limited WAT-like module and a tiny assembler in `lib/wasmWatRunner.mjs`. This keeps the demo self-contained and makes the WASM boundary visible. It is not a Rust compiler and should not be presented as one.

The accepted module shape is:

```wat
(module
  (func (export "shade") (param i32) (result i32)
    local.get 0
    i32.const 7
    i32.mul
    i32.const 255
    i32.rem_u
  )
)
```

The runner accepts one `i32` parameter, one `i32` result, at most 64 instructions, and no imports. It supports `local.get`, `i32.const`, and a small set of integer arithmetic/bitwise operations. It validates the generated bytes with `WebAssembly.validate` before instantiation.

## WebGPU path

`components/WebGpuWasmPlayground.tsx` performs capability detection in a client effect:

1. Check `navigator.gpu`.
2. Request an adapter and a device.
3. Configure the canvas with `navigator.gpu.getPreferredCanvasFormat()`.
4. Create a WGSL shader module and render pipeline.
5. Write the WASM result into a 16-byte uniform buffer.
6. Submit a render pass containing one triangle.

If WebGPU is missing or no adapter is returned, the WASM runner remains usable and the status text explains the fallback. This matters because WebGPU requires a secure context and browser, OS, driver, and GPU support are not identical.

## Rust production path

The live editor is intentionally tiny, but the production Rust flow is the same one used by the Game of Life sibling project:

```bash
wasm-pack build --release --target web --out-dir pkg
```

The Rust crate should export a narrow, typed API with `#[wasm_bindgen]`. A browser entry point loads the generated module and calls `await init()` before using the exports. Keep the generated package versioned and separate from the blog bundle if the module grows beyond a small teaching example.

For a future full editor, prefer a separate sandboxed playground origin or worker. Do not add a remote Rust compiler to the normal blog route. The architecture notes already require normal blog pages to download zero playground JavaScript; this component is only pulled into the article that uses it.

## Verification

Run the pure WASM compiler tests:

```bash
yarn test:wasm-runner
```

Run formatting and the production build:

```bash
yarn prettier --check components/WebGpuWasmPlayground.tsx lib/wasmWatRunner.mjs scripts/wasm-wat-runner.test.mjs data/blog/webgpu.mdx docs/webgpu-wasm-mdx-runner.md
yarn build
```

For browser verification, open the draft route in a WebGPU-capable browser, change `i32.const 7` to another integer, press **Run WASM**, and confirm both the numeric result and the triangle color change. Then repeat with WebGPU disabled: the result should still appear and the status should explain why the canvas did not render.
